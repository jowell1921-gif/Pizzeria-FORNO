# 0006 — Backend y API (Fase 5)

Fecha: 2026-11-07

| Tema                 | Decisión                                                                                                                                                                                                                                                   |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Alcance              | Lectura pública (carta, promociones, local, zonas), seguridad transversal y documentación. La escritura de pedidos, canjes, administración y pagos queda para sus fases (6–9)                                                                              |
| Contrato             | Esquemas Zod de respuesta únicos (`src/docs/schemas.ts`). Generan el OpenAPI 3.1 (`z.toJSONSchema`) y se usan en pruebas de contrato contra PostgreSQL real. Una prueba de contrato ya detectó que `orderNumber` es un entero y no una cadena              |
| Documentación        | `/api/v1/openapi.json` y Swagger UI servido desde el propio servidor (`swagger-ui-dist`), sin CDN: así la CSP de Helmet no se relaja. En producción solo si `API_DOCS_ENABLED=true`                                                                        |
| Límite de peticiones | `express-rate-limit`: por IP a toda la API, por usuario y más estricto en escrituras. Errores `429` con el formato de la API. `/health` queda fuera. Almacén en memoria (una sola instancia); si se escala a varias réplicas habrá que usar uno compartido |
| Proxy                | `TRUST_PROXY` explícito (0 por defecto, 1 en Railway). No se confía en `X-Forwarded-For` salvo que se indique, para que no se pueda esquivar el límite cambiando la cabecera                                                                               |
| Registros            | `pino` + `pino-http`, JSON de una línea por petición con `requestId`. Solo método, ruta (sin consulta), código y duración; nunca cabeceras ni cuerpos (podrían contener tokens o datos personales). Los errores inesperados se registran con su pila       |
| CORS                 | Orígenes explícitos, métodos y cabeceras acotados; se exponen `X-Request-Id` y las cabeceras de límite                                                                                                                                                     |
| Caché                | `Cache-Control` público de 30 s en los datos públicos                                                                                                                                                                                                      |
| Datos públicos       | El local no expone datos fiscales internos. Los cupones personales (`userId`) nunca se listan. Que una promoción sea aplicable a un pedido lo decide el servidor al crearlo                                                                                |
| Horario              | `open` se calcula en el servidor con la zona horaria del local, los días especiales y el horario semanal (día ISO 1–7). La hora del cliente nunca se usa                                                                                                   |
| RLS                  | Las tablas de negocio mantienen RLS activado sin políticas (migración `rls_default_deny`): el acceso directo con las claves de Supabase queda denegado y todo pasa por esta API. Se revisará de nuevo al añadir Storage (fase 8)                           |
| Idempotencia         | La tabla `IdempotencyRecord` ya existe; el middleware `Idempotency-Key` se implementa con el primer `POST` real (pedidos, fase 6) para probarlo con un caso real                                                                                           |
